# MCP 태스크 ↔ GitHub PR 연결

## 요청 내용

gdc-service에 추가된 [#512 [깃허브 연동] PR ↔ 태스크 연결](https://gdc.gemiso.com/tasks/15918) 기능을
MCP에서도 쓸 수 있게 한다. 태스크에 PR을 연결·해제하고, 연결된 PR을 조회한다.

## 배경

gdc-service `develop`에 Phase 1이 들어가 있다(PR #188, `7e3b344`, 2026-08-28 머지).
MCP 쪽만 이 경로를 안 쓰고 있다.

- `GET  /api/tasks/tasks/{id}/github-pr-candidates/` → `{repos, candidates, failed_repos}` (GitHub 실시간 조회)
- `POST /api/tasks/tasks/{id}/github-pull-requests/` `{repo_link_id, pr_number}` → 수동 연결(201)
- `DELETE /api/tasks/tasks/{id}/github-pull-requests/{pr_id}/` → 해제(204)
- `GET  /api/integrations/github/repo-links/?project={id}` → 프로젝트의 GitHub 레포 연결 목록(GitHub 호출 없음)
- 태스크 상세 응답에 `github_pull_requests[]`가 이미 실려 오는데, 현재 `get_task`가 읽지 않고 버린다.

자동 연결(PR 본문 파싱)은 서버·웹훅이 처리하므로 MCP가 손댈 부분이 없다.
MCP가 채워야 할 것은 **수동 경로**다.

### 서버 API의 두 가지 걸림돌

1. **연결은 `repo_link_id`(GDC 내부 id)를 요구한다.** 사용자는 이 값을 모르고 말할 수도 없다.
   → 도구는 `repo="owner/repo"`로 받고, **repo-links 목록**에서 매칭해 내부 id로 바꾼다.
   프로젝트에 연결된 레포가 1개면 `repo` 생략을 허용한다.
2. **해제는 `pr_id`(GDC PR 행 id)를 요구한다.** 사용자가 말하는 건 `#123`(PR 번호)이다.
   → 태스크 상세를 1회 읽어 `github_pull_requests`에서 번호로 매칭해 내부 id를 찾는다.
   상세 항목에 `repo_full_name`이 있으므로 **해제는 repo 해석용 추가 호출이 필요 없다.**

### 선행 검토에서 드러난 제약 (2026-08-28)

- **서버 미배포**: 운영(`gdc.gemiso.com`)·개발(`se.gemiso.com:11521`) 모두
  `github-pr-candidates`가 **404**(같은 태스크 상세는 401 → 라우트 자체가 없음).
  develop 머지가 당일이라 아직 어느 환경에도 올라가지 않았다.
- 따라서 이번 작업은 **구현·순수 로직 테스트까지만** 하고,
  **종단 검증(7단계)과 버전 상향·릴리스는 서버 배포 후로 보류**한다(사용자 결정).

## 설계

### 도구 4건

| 도구 | 시그니처 | 동작 |
|------|----------|------|
| `get_task` (기존) | — | 응답에 `pull_requests[]` 추가 |
| `list_task_pr_candidates` | `(task_id)` | 붙일 수 있는 최근 PR 후보 + 연결 가능 레포 목록 |
| `link_task_pr` | `(task_id, pr_number, repo=None)` | PR 연결 |
| `unlink_task_pr` | `(task_id, pr_number, repo=None)` | 연결 해제 |

`repo`는 `"owner/repo"` 문자열. 생략 시 후보가 1개면 자동 선택하고,
여러 개면 **오류로 세우고 목록을 안내**한다(엉뚱한 레포에 붙이는 것보다 낫다).

### 레포 해석 경로 (성능)

`github-pr-candidates`는 **레포마다 GitHub을 실시간 호출**한다(httpx timeout 30초에 걸릴 수 있음).
연결 도구가 레포 이름만 해석하려고 이 경로를 쓰면 값이 비싸다.
→ `link_task_pr`은 `GET /api/integrations/github/repo-links/?project={id}`를 쓰고,
서버와 **같은 조건**을 클라이언트에서 건다: `detached_at is null ∧ sync_enabled ∧ installation_active`.
후보 목록이 필요한 `list_task_pr_candidates`만 candidates 경로를 쓴다.

### `pull_requests` 항목 모양

```
{ id, number, title, url, repo_full_name, state, merged_at, base_branch, source }
```

- `id`: GDC 내부 PR 행 id (해제에 쓰인다)
- `state`: `open` / `draft` / `closed` / `merged`
- `source`: `manual` / `auto` / `auto_issue` — 자동 링크는 PR **본문의 근거**를 지우지 않으면
  해제해도 다음 PR 수정에서 다시 붙는다. 근거는 `auto`=태스크 링크(`/tasks/{id}`),
  `auto_issue`=이슈 참조 키워드(`관련 이슈: #15`). 해제 응답에 source별로 안내한다.
- 필드명은 서버(`repo_full_name`)를 그대로 따른다 — 입력 파라미터 `repo`와 헷갈리지 않게 한다.

### 후보 항목 모양

```
{ repo_link_id, repo_full_name, number, title, state, updated_at, linked }
```

- `linked`: 이미 이 태스크에 붙어 있는 PR. 그대로 노출해 중복 연결 시도를 막는다.
- `failed_repos[]`: `{repo_full_name, detail}` — 서버가 사용자용 안내 문구를 만들어 주므로 그대로 전달한다.

### 오류 전달

서버는 400 `detail`에 사용자용 문구를 담는다("…에 해당 번호의 PR이 없습니다",
GitHub App 권한 미부여 안내, "이 프로젝트에서 사용할 수 있는 GitHub 연결이 아닙니다").
`client.raise_for_status()` 때문에 그대로 두면 `HTTPStatusError`로 뭉개지므로,
기존 패턴(`server.py`의 403 → `ValueError` 변환)대로 **400/403을 잡아 `detail`을 한글 오류로 옮긴다.**
연결·해제는 쓰기 권한과 프로젝트 종료 여부를 서버가 강제한다(403).

### 순수 로직 분리 (테스트 대상)

- `_pick_repo_link(links, repo)` — 이름 매칭·단일 자동 선택·다중 시 후보 안내 오류
- `_find_linked_pr(prs, pr_number, repo)` — 번호(+레포) 매칭으로 내부 `id` 찾기
- `_pr_summary(pr)` — 상세 응답 항목 → MCP 응답 모양

### 하지 않는 것

- 슬래시 커맨드/프롬프트 추가 — 4건 모두 자연어 호출로 충분하고,
  `/gdc-*` 커맨드는 여러 단계를 묶는 흐름에만 둔다.
- 자동 연결(본문 파싱) 관련 기능 — 서버·웹훅 소관이다.
- PR 상태 → 태스크 상태 자동 전이 — 서버 Phase 2로 분리돼 있다.

## 참고 사항

- **선행 조건**: GitHub App에 `Pull requests: Read-only` 권한이 있어야 하고, 기존 설치는
  **재승인**해야 열린다. 없으면 후보 조회가 `failed_repos`에 사유와 함께 담겨 온다
  (서버가 안내 문구를 만들어 주므로 MCP는 그대로 전달한다).
- **검증 제약**: (1) 서버 미배포 — 배포 전에는 모든 경로가 404. (2) 배포 후에도 테스트
  프로젝트(워크스페이스 3)에 GitHub 레포 연결이 없으면 후보가 빈 배열이라 연결·해제
  종단 검증을 못 한다. 그 경우 사용자에게 알리고 검증 범위를 문서에 명시한다.
- 변경 파일: `gdc_mcp/server.py`, `tests/test_pr_link.py`(신규), `README.md`
  (`.claude-plugin/plugin.json`은 배포 후 버전 상향에서 함께 손댄다)
